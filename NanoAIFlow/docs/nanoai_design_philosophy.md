# NanoAI 设计思想（当前实现）

> 本文说明 NanoAI 在当前代码中的核心设计取向，聚焦“静态类型管线 + 阶段化并发 + 顺序放行”。

## 1. 目标

NanoAI 关注的不是“动态拼装任意节点”，而是：

- 在固定业务链路中，提供高吞吐并发执行。
- 保证输出行为稳定、可解释。
- 用明确的类型签名降低运行期类型错误。

## 2. 核心取舍

### 2.1 静态类型优先

- 每个 Pipe 的输入输出由 `on_run(...)` 的签名定义。
- 管线类型在编译期确定：`NanoPipeLine<P1, P2, ...>`。
- 不走 `std::any` 动态分发路径，减少运行时类型不确定性。

### 2.2 并发与顺序并重

- 阶段内部支持并发执行（受 `concurrency()` 约束）。
- 阶段间按全局序号顺序放行，保证语义稳定。

### 2.3 执行策略可配置

- `shared_pool`：统一共享线程池，资源利用率高。
- `dedicated_pool`：关键阶段隔离资源，避免互相干扰。
- `inline_run`：轻量任务零调度开销。

## 3. 一次 run 的路径

1. 调用 `pipeline.run(...)` 分配序号 `seq`。
2. 进入第 1 阶段并发执行。
3. 阶段完成后等待顺序条件（`seq == next_forward_seq`）再向下游传递。
4. 依次推进，直到末阶段输出。

结果：
- 高并发下依然保持可预测的顺序语义。
- 下游逻辑不需要额外处理乱序补偿。

## 4. 类型流转规则

- 普通返回值：直接作为下一阶段输入。
- `std::tuple<...>` 返回：下一阶段自动展开为多参数调用。

这使得“打包/解包”在框架层完成，业务代码更聚焦于变换逻辑。

## 5. 为什么不强调运行时增删节点

当前实现重点是：
- 编译期可验证的类型正确性。
- 稳定高效的执行路径。

因此更适合“结构相对固定、数据量大、并发要求高”的推理前后处理链路。

## 6. 适用场景

- CV/NLP/语音等端侧推理前后处理流水线。
- 多阶段处理且要求稳定吞吐和可追踪行为的服务。
- 希望减少运行时类型错误、提高重构安全性的工程。

## 7. 工程建议

1. 明确每个 Pipe 的输入输出契约。
2. 重阶段（耗时）提高并发，轻阶段降低并发，减少争用。
3. 优先用 `make_pipeline_builder(...)` 构建长链，避免误用 `add_pipe` 返回值。
4. 在基准测试中同时关注吞吐、尾延时和顺序一致性。
